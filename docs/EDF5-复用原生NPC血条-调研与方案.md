# 复用游戏原生 NPC 血条 —— 调研与方案

目标：不再用"分层透明窗口 + 自绘"，改成**借用游戏自己的 HUD 绘制**来显示敌人血条。
动机有三个：

1. **延迟**：HUD 在游戏渲染管线里同帧绘制，转视角时与模型完全同步（覆盖层方案天然落后 1~2 帧）。
2. **性能**：不再有 14.4 MB/帧的清屏与整屏提交（见 `EDF5-血条延迟与卡顿-分析与优化方案.md`）。
3. **样式**：字形、描边、缩放规则天然与游戏一致，不用自己调。

---

## 一、已经定位到的原生类

EDF5 保留了完整 MSVC RTTI，用 `tools\edf5rtti.py` 可以直接按名字找 HUD 元素：

| 类 | vtable (RVA) | 备注 |
|---|---|---|
| `.?AVHudPlayer_FollowerDurability@@` | `0xEC92F8` | **就是队友/NPC 血条**（td `0x11C0688`，col `0xF8B908`） |
| `.?AUInitParam@HudPlayer_FollowerDurability@@` | `0xEC9140` | 它的初始化参数结构 |
| `.?AVHudPlayer_CrossHair@@` | `0xEC92A0` | 准星 |
| `.?AVHudPlayer_Chat@@` | `0xEC9260` | 聊天 |
| `.?AVHudPlayer_MultiPlayStatus@@` | `0xEC9390` | 联机状态 |
| `.?AVHudPlayer_RescueMessage@@` | `0xEC9500` | 救援提示 |
| `.?AVEventFactor_ObjectDurability@@` | `0xE98AE0` | 与"对象耐久"相关的事件因子 |

没有 `LifeBar` / `HealthBar` / `Gauge` 这类命名，说明血条是画在 `HudPlayer_FollowerDurability`
的绘制流程里的（不是独立的 GUI 控件）。

### vtable 实体槽（`0xEC92F8`）

```
slot  0 -> 0x024980  (size 0x0    ← 无 .pdata 边界，可能是跳转桩/共享函数)
slot  1 -> 0x023390  (size 0x0    ← 同上，slot1/2 同一个函数)
slot  2 -> 0x023390
slot  3 -> 0x4B9D30  (0x46)
slot  4 -> 0x4B9CB0  (0x7B)
slot  5 -> 0x4B41E0  (0xD4)   ← 最可能是 OnUpdate
slot  6 -> 0x4B42C0  (0x94)   ← 最可能是 OnDraw
slot 16 -> 0x4BAB80  (0x09)
slot 17 -> 0x4BAB10  (0x1C)
```

### 已排除的可能

把上面每个槽函数整体反汇编后扫描 RIP 相对引用，**没有**任何一个直接引用：

- `0x125AB80` TeamManager（我们在用的队伍表）
- `0x125AB68` 玩家链
- `0x125B080` 相机链

→ 结论：**跟随者列表不是每帧从全局队伍表现取的**，多半是 HUD 初始化时被灌进 HUD 对象自己的成员
（数组/`std::vector`）里，之后每帧遍历自己的成员。要接管它，就得先找到那个容器。

## 二、三条可选路线

### 路线 A：把敌人塞进它遍历的列表（改游戏数据）

找到那个"跟随者列表"，把敌方对象指针临时塞进去，让游戏**原生**给敌人画条。

- 优点：改动最小，样式 100% 原样，实现最快。
- 缺点：**污染游戏自己的 UI 状态**。列表很可能同时被其它系统读（救援、联机显示、AI），
  塞入敌人可能引发奇怪行为；联机时属于"改游戏数据"，风险最高。需要每帧插入/移除，容易漏。
- 结论：只适合做**可行性验证**，不适合作为最终方案。

### 路线 B：直接调用它的"画一条"函数

找到 `HudPlayer_FollowerDurability` 里真正落笔的那个 2D 图元调用（矩形/贴图），
我们自己在合适的时机对每个敌人调用一次。

- 优点：不改游戏数据，样式一致。
- 缺点：那个函数的参数结构（位置、宽度、比例、颜色、材质句柄）需要完全逆向出来；
  它可能依赖 HUD 对象内部的若干已初始化成员（DC/材质/布局），脱离 HUD 上下文调用会崩。
- 结论：技术含量最高、最脆。

### 路线 C（推荐）：用游戏的 HUD 时机 + 投影 + 图元，画我们自己的条

不碰游戏数据，只复用**时机**和**工具函数**：

1. 找到游戏 HUD 绘制阶段的稳定挂点（而不是现在的 `Present`），在**同一时机**绘制；
2. 复用游戏自己的"世界坐标 → 屏幕坐标"投影（HUD 用的那套，天然匹配 UI 缩放）；
3. 复用游戏的 2D 图元绘制（画矩形/贴图，而不是 GDI）；
4. 血条的位置/比例仍由我们自己算（沿用现在的采集与过滤逻辑）。

- 优点：**同时解决延迟与卡顿**（无独立窗口、与 UI 同帧）；不污染游戏状态；
  联机风险与现在同级（只读 + 自己画）；样式可以逼近原生。
- 缺点：要摸清 HUD 的绘制上下文与图元接口；需要判断 HUD 绘制挂点在各分辨率/UI 缩放下的稳定性。
- 结论：作为主方案推进，A 只用来做交叉验证。

## 三、下一步的具体动作

1. **找列表来源**：反查谁构造/初始化了 `HudPlayer_FollowerDurability`
   （线索：`InitParam` vtable `0xEC9140`，以及 `0xEC92F8` 的对象在谁那里被 new）。
2. **读清 slot 5/6**（`0x4B41E0` / `0x4B42C0`）：遍历成员 → 取对象坐标 → 投影 → 落笔，
   这条链就是我们需要复用的形状。
3. **定位 2D 图元绘制**：从 slot6 的下游调用里找绘制函数（数值上应能看到矩形顶点、
   UV/材质、颜色四个分量）。
4. **定位 HUD 绘制时机**：找一个"HUD 阶段"的挂点（比 `Present` 更早、且在 UI 绘制前），
   确认它每帧调用一次、各分辨率下都走同一条路径。
5. **验证方式**：先用路线 A 做**一次性验证**（仅在单机测试时把 1 个敌人塞进列表看是否出现原生条），
   确认"能复用"之后再投路线 C。

## 四、已知风险

- **联机**：路线 A/C 都要避免修改游戏对象或列表；路线 C 只读，风险与现有实现同级。
- **版本脆弱**：HUD 类地址随游戏更新变化 → 沿用现有的版本自检思路（字符串/AOB 校验，不匹配就不启用）。
- **UI 缩放/分辨率**：HUD 可能使用虚坐标或按分辨率缩放的画布，投影函数必须用它的那套，
  不能继续用我们现在的 `BuildViewProjection`（那是主渲染相机的）。
- **遮挡**：遮挡判定与绘制时机无关，可原样保留；但一旦绘制移入 HUD 阶段，
  射线仍在渲染线程上跑，注意不要引入新的时序问题。

## 五、逆向进展（2026-10-10，v1.0.8 基线）

### 5.1 完整调用链（已确认）

```
0x4B47B0  资格判定/创建入口  （arg1 = 被监视对象）
   └─ 0x4B5210  「给一个对象创建原生耐久条」  ← 只有这一个调用者
        ├─ [param+8] = arg1          （把被监视对象写进 InitParam）
        ├─ operator new(0x90)
        ├─ 0x4B9B90  HudPlayer_FollowerDurability 构造函数（唯一构造点，+0x4B9C04 写虚表 0xEC92F8）
        ├─ 0x4B5F60 / 0x4B51A0       把新对象插进 [arg1 + 0x188] 的容器
        └─ 0x36A8D0 / 0x4B5B60       取回句柄写进调用者的 out 参数（引用计数智能指针）
```

绘制路径（虚表 `0xEC92F8`）：

```
slot3 = 0x4B9D30   OnDraw(this, a2, a3)
   ├─ [this+0x78] 非空 && [that+8] != 0 && [this+0x80]→[+0xDC6] != 0   （可见性/HUD 开关）
   ├─ 0x4B4360                          （取当前画布/上下文，入参 rcx=this）
   ├─ rcx = [this+0x18]                 ← 被监视对象
   ├─ 0x624730(obj, &matrix)            ← 生成朝向相机的 billboard 矩阵
   ├─ xmm2 = [obj+0x118] / [obj+0x11C]  ← 血量比（**int32**，不是我们的 +0x1F8/+0x1FC 浮点）
   ├─ 0x5BE600(ratio, [obj+0x24], [obj+0x28], [obj+0x2C], &rect)
   ├─ 4x4 矩阵乘（把 rect 的 4 个列向量变换过去）
   └─ 0x4B9EB0(this, &matrix, [this+0x80], a2, a3)   ← 真正落笔
         └─ rdi = [[r8+0x3A8]]  遍历一个循环链表，每条目 [+0x10]→[+0xA0] 取世界坐标做变换
```

### 5.2 关键对象布局（`HudPlayer_FollowerDurability`，0x90 字节）

| 偏移 | 含义 |
|---|---|
| `+0x00` | 虚表 `0xEC92F8` |
| `+0x10` | 引用计数对象（构造时清零，随后由句柄赋值） |
| `+0x18` | **被监视对象**（构造时取自 `InitParam+8`） |
| `+0x24/+0x28/+0x2C` | 条几何用的浮点（在被监视对象上，`0x5BE600` 的入参） |
| `+0x60` | 启用标志（slot5/slot6 都先 `cmp [rcx+0x60], 1`） |
| `+0x70` / `+0x78` | 持有者/上下文（引用计数；slot4 负责释放） |
| `+0x80` | 渲染上下文指针（`[+0xDC6]` 是 HUD 可见开关） |

**InitParam**（很小，栈上构造）：`+0x00` = 一个类型/工厂指针（来自 `rip+0xA14911`），
`+0x08` = 被监视对象（由 `0x4B5210` 自己写入），`+0x10` = 一个引用计数持有者。

### 5.3 由这条链得到的两条可行子路线

**C1 — 让游戏自己创建原生血条对象**（最省事）：

我们自己调用 `0x4B5210(enemyObj, &outHandle, &param)`，游戏就会为这个敌人创建并注册一个
原生耐久条对象，之后由游戏自己的 HUD 绘制流程渲染 —— **没有覆盖层、没有延迟、没有 14.4 MB 清屏**。

- 需要搞清楚：`0x4B47B0` 里 `0x9C8228(arg2, 0, str1, str2)` 到底查了什么（`param+0x10` 的来源）、
  以及 `enemyObj+0x188` 这个容器在敌人身上是否已初始化。
- **风险**：这会**写游戏对象数据**（往敌人实体里插一个 HUD 挂件），敌人死亡/关卡结束必须清理干净；
  联机场景风险最高，需要谨慎评估。

**C2 — 只复用绘制原语**（最干净）：

在游戏 HUD 绘制阶段挂点，自己维护"敌人 → 屏幕坐标/比例"的数组，复用
`0x624730`（billboard 矩阵）与 `0x4B9EB0`（四边形落笔）来画。

- 不写游戏数据；样式与原版一致；同样没有覆盖层延迟。
- 需要摸清 `0x4B9EB0` 的入参契约（矩阵 + 上下文 + 最后两个参数）与 `[ctx+0x3A8]` 那个链表的作用。

### 5.4 必须先回答的一个问题

原生条的**血量比取自 `+0x118`/`+0x11C`（int32）**，而我们一直用的是 `+0x1F8`/`+0x1FC`（float32）。
走上原生路线前必须先确认：

1. 这两个 int32 在**敌人**对象上是什么（是否也是"当前/最大耐久"）；
2. 如果不是，C2 路线能不能绕开它（我们自己算比例、只用它的绘制原语）——C2 天然绕开，
   因为它只是借绘制函数，比例由我们提供。

→ 这也说明 **C2 比 C1 更稳**：C1 依赖游戏自己读那个字段，C2 完全由我们控制比例与位置。

## 六、C1 路线的精确契约（2026-10-10 第二轮逆向）

用户决定走 **C1（尽可能用原生）**，因此必须精确复制游戏的创建契约。

### 6.1 类型链（关键）

`0x9C8228` 不是游戏函数，而是 **导入 thunk：`__RTDynamicCast`（VCRUNTIME140.dll，IAT 槽 `0xC97918`）**。
把它还原出来后，整条链的类型约束就明确了：

| 位置 | 转换 | 说明 |
|---|---|---|
| 调用者 `0x55D70` / `0x56145` | `SceneObject` → `GameObjectBase` | 先把场景对象收敛到游戏对象基类 |
| `0x4B47B0+0x063` | `GameObjectBase` → **`SoldierBase`** | **失败即 `return`，不创建任何条** |

涉及的类型描述符 RVA：`0x11A49C0` = `.?AVSceneObject@game@xgs@@`、
`0x11A4948` = `.?AVGameObjectBase@@`、`0x11A4970` = **`.?AVSoldierBase@@`**。

**结论：原生耐久条只服务 `SoldierBase` 派生对象。** 敌人的类（`GiantAnt` / `Deiroi` /
`Humanoid_*` / `InsectBase` …）是否派生自 `SoldierBase` 是 C1 能否成立的第一道门槛。

### 6.2 `0x4B5210` 的入参契约

```
0x4B5210(void* watched /*rcx*/, void** outHandle /*rdx*/, InitParam* param /*r8*/)
```

`InitParam`（栈上小结构，虚表 = `0xEC9140` = `.?AUInitParam@HudPlayer_FollowerDurability@@`）：

| 偏移 | 内容 | 来源 |
|---|---|---|
| `+0x00` | 虚表 `0xEC9140` | 调用点 `0x4B4828: lea rax,[rip+0xA14911]` → 实测 = `0xEC9140` |
| `+0x08` | 被监视对象 | 由 `0x4B5210` 自己写入（= 它的 arg1） |
| `+0x10` | **owner/上下文：一个 `SoldierBase*`** | `dynamic_cast<SoldierBase*>(arg2)` 的结果 |

构造函数 `0x4B9B90` 里 `+0x10` 的去向：`mov rcx,[rsi+0x10]; call 0x4FC30` → 存入 `hudObj+0x70`/`+0x78`
（引用计数句柄），同时 `mov [rbx+0x80], rax` 把 `SoldierBase*` 原样存进 `hudObj+0x80`。

而 slot3（`0x4B9D30`）的可见性门槛正是：

```
[this+0x78] != 0 && [[this+0x78]+8] != 0 && [[this+0x80]+0xDC6] != 0
                                        ^^^^^^^^^^^^^^ SoldierBase+0xDC6 上的一个标志字节
```

→ **`param+0x10` 必须是一个真实的、`+0xDC6` 标志为真的 `SoldierBase` 对象，否则条永远不会被画。**
最省事的取值：直接借用一个已经存在且正在工作的条对象的 `+0x70/+0x78/+0x80`（即复用玩家/友军那套 owner）。

### 6.3 还有两个必须先验证的前置条件

1. **`+0x118` / `+0x11C`（int32）在敌人对象上是不是「当前/最大耐久」。**
   原生条的比例完全取自这两个字段（slot3：`divss xmm2, xmm0`），而我们一直用的是
   `+0x1F8`/`+0x1FC`（float32）。如果敌人身上这两个 int 不是耐久，C1 画出来的比例就是错的，
   此时要么放弃 C1、要么只当作"位置/样式原生、比例需另找来源"。
2. **`watched + 0x188` 容器在敌人对象上是否已初始化。**
   `0x4B5210` 会把新条插进 `[watched + 0x188]` 的容器（`lea rcx,[rdi+0x188]; call 0x4B51A0`）。
   若该容器在敌人身上无效，插入会破坏敌人对象 → 必须先确认它属于基类初始化的一部分。

### 6.4 建议的实施顺序（先只读、后写入）

1. **只读探针阶段**：在渲染线程上
   - 扫描堆/对象表，找到至少一个现存的原生条对象（vtable = `0xEC92F8`），记录它的
     `+0x18`（被监视对象）、`+0x70`/`+0x78`/`+0x80`（owner/上下文）；
   - 对若干敌人 dump `+0x118`/`+0x11C`/`+0x24`/`+0x28`/`+0x2C`/`+0x1F8`/`+0x1FC`；
   - dump 敌人对象上 `+0x188` 处的三个指针（容器 begin/end/cap）看是否像合法容器；
   - **只记日志，不创建任何东西** → 一次实机就能判定 C1 是否可行。
2. **写入阶段**（前置条件都成立时）：调用 `0x4B5210(enemy, &handle, &param)`，
   `param = {0xEC9140, 0, ownerFromStep1}`，把返回的句柄存起来（引用计数，不能丢），
   敌人死亡/换关卡时释放并清空 `+0x188` 里的残留。全程 `__try/__except` 包裹，并做成 ini 开关
   `NativeBars=0/1`，默认 0，确认稳定后再默认开。

## 七、只读探针实测结果（v1.0.9，2026-10-10）——C1「全原生」被否定

实机跑了一局（63 条敌人 dump，全部 `GiantAnt`；部分时段友军对象 18~19 个）：

| 检查项 | 实测 | 结论 |
|---|---|---|
| 敌人转 `SoldierBase` | `Soldier=0`（63/63） | 敌人**不是** `SoldierBase` 派生（符合预期；直接调 `0x4B5210` 仍可绕过该门槛） |
| `[watched+0x118]` / `[+0x11C]`（原生条比例来源，int32） | 在 GiantAnt 上实为两枚 **float：`-20.0` / `1.0`** | 当作 int 相除是**无意义的垃圾** → 原生条比例源在敌人身上不成立 |
| `[watched+0x24]/[+0x28]/[+0x2C]`（原生条几何浮点） | `0.0` / 垃圾 / `0.0` | 敌人身上同样无意义 |
| `[watched+0x188]`（原以为是条对象的容器） | 读出来是浮点数据 `1.0 / 0 / 0 / 1.0`（RGBA 样） | **不是容器**；`0x4B51A0` 更可能是"把句柄写进某个字段"而非插入容器 |
| 找出现成的原生条对象（vtable `0xEC92F8`） | **0 个** | 因此也拿不到可借用的 owner（`+0x70/+0x78/+0x80`）样板 |

**结论：原生条的"比例/几何"完全取自被监视实体自身的类型相关字段。**
对 `SoldierBase` 派生对象（玩家/友军）那些字段才是耐久；对敌人（`GiantAnt` 等）是别的数据。
所以 **C1 无法做到"把敌人交给游戏、让游戏自己算并画"**——除非：

- **C1-fake**：我们自己造一个"被监视对象"（假结构：填敌人位置 + 把我们的比例写进那两个 int 字段 + 填几何），
  再调 `0x4B5210(fakeObj, …)` 让游戏渲染。外观最原生，但需要把 slot3 与 `0x624730` 从被监视对象上读的
  **所有字段**逆清楚（现在还只确认了 `+0x18/+0x24/+0x28/+0x2C/+0x118/+0x11C/+0x1A0/+0x188`），风险高。
- **不要写敌人字段**：往敌人的 `+0x118/+0x11C` 写我们的血量属于改动游戏数据（那两个字段本是 float `-20.0`/`1.0`，
  很可能是伤害倍率/颜色之类），会破坏游戏逻辑，**不做**。
- **C2**：只借绘制原语（`0x624730` billboard 矩阵 + `0x4B9EB0` 四边形落笔），比例与位置全由我们提供。
